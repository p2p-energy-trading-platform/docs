Order Validation and Lifecycle
==============================

- **Status:** Draft v2. Open decisions are resolved as proposals. Items marked *Needs sign-off* require the named owner's agreement before implementation.
- **Evidence base:** `docs` PR #87 (commit `959decc`), `protobuf` `v1.17.1`, and the code of `matching-engine`, `iot-ingestion-dispatch`, `api-gateway`, `auth-service`, `billing-wallet-service`, and `gridx-infra` as of 2026-11-02. Where documents and code disagree, the shipped code and the `protobuf` repository are the source of truth.

Purpose
-------

The Order Service validates order requests, persists their durable records, and coordinates their submission to the Matching Engine. It does not perform matching itself.

The Order Service has no HTTP server. It exposes a gRPC `OrderService` called only by the API Gateway, and it communicates with the Matching Engine only through Kafka.

Validation, persistence, event publication, and Matching Engine acceptance are separate stages. The API communicates the outcome of the stage actually reached. A persisted order is never reported as accepted, and an accepted order is never reported as executed.

| Stage | Where it happens | Visible to the client as |
|---|---|---|
| Validation | Order Service, before any write | gRPC error, nothing persisted |
| Persistence | PostgreSQL transaction | `OK` with order `status = PENDING` |
| Publication | Outbox publisher to Kafka | still `PENDING` |
| Matching Engine acceptance | Matching Engine update event | `OPEN` or `REJECTED` |
| Execution | Matching Engine update events | `PARTIALLY_FILLED`, `FILLED` |

Conventions
-----------

### Units and representation (D-02)

| Concept | Representation | Notes |
|---|---|---|
| Energy quantity | `int64`, watt-hours (Wh) | Engine `Quantity`. 1 kWh = 1000 Wh. |
| Price | `int64`, micro-AED per kWh | Engine `Price`. 1 AED = 1,000,000 micro-AED. The grid fee uses the same unit. |
| Price tick | 10,000 micro-AED (1 fil) | Prices are whole fils so they match what users see. |
| Timestamps | UTC | `TIMESTAMPTZ` in PostgreSQL, `google.protobuf.Timestamp` on the wire. |
| Order ID | `uint64` | Generated by the Order Service from a PostgreSQL identity sequence. The gateway may serialize it as a string for JavaScript clients. |

- No binary floating point is used for quantities or prices. The only floating-point value is the IoT `rated_solar_kw`, converted once to an integer capacity at the boundary (see D-04).
- Trade value in micro-AED is `price x quantity_wh / 1000`. The engine's internal `buyerTotalPrice` is the raw product `(price + fee) x Wh`, and `TradeExecuted` does not carry it. Settlement computes amounts from `execution_price`, `grid_fee_per_kwh`, and `quantity`.
- The Order Service never computes monetary totals. Billing owns rounding when posting to wallets (wallets use minor units of 1/100 credit).
- The engine labels the currency AED, while some documents say RM. This document uses AED, matching the engine.
- `OrderAccepted.remaining_quantity` is a `double` in the current proto. The Order Service always sets it equal to `quantity`. It is deprecated in favour of `OrderUpdated.remaining_quantity` (`int64`), because retyping it would be a breaking change under the repository's `buf` rules.

Order Model
-----------

| Field | PostgreSQL type | Wire mapping | Constraints and notes |
|---|---|---|---|
| `order_id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | `order_id` (`uint64`) | Primary key. |
| `user_id` | `UUID` | `user_uuid` (new) | Auth user ID, taken from the gateway-propagated principal, never from the order payload. |
| `trader_id` | `BIGINT` | `user_id` (`uint64`) | Numeric trader number sent to the engine, issued from `trader_accounts` (D-11). |

| `terminal_source` | enum | not on the wire | `ME` or `RECONCILER`. |
| `needs_reconciliation` | `BOOLEAN NOT NULL DEFAULT FALSE` | not on the wire | Set when an event cannot be applied safely. |
| `idempotency_key` | text | not on the wire | `UNIQUE (user_id, idempotency_key)`. |
| `request_fingerprint` | `BYTEA` | not on the wire | SHA-256 of the canonical request. |
| `created_at`, `updated_at` | `TIMESTAMPTZ NOT NULL` | `created_at`, `updated_at` | UTC. |
| `expires_at` | `TIMESTAMPTZ` | `expires_at` | LIMIT: equals `delivery_slot_end`. MARKET: `min(created_at + MARKET TTL, delivery_slot_end)`. Not client-settable. |

Table DDL and supporting tables (`trader_accounts`, `order_status_history`, `outbox_events`, `processed_events`, `consumer_dead_letters`, `energy_slot_capacity`, `energy_allocations`) are specified in the PostgreSQL persistence document, in the `order_management_data` schema. This document defines the rules they must enforce.

Validation Rules
----------------

Checks run in this order so cheap, deterministic failures happen before any network call.

1. **Identity:** The request carries `owner_user_id` (UUID), set by the gateway from the access token, the same pattern the gateway uses for IoT calls. It must be non-empty, and equal to the `x-gridx-user-id` metadata when that is present.
2. **Authorization:** `CreateOrder` calls Auth `CheckPermission(user_id, "trade:create")`. The result is cached for 60 s, and a failure to reach Auth fails closed (`AUTH_UNAVAILABLE`). View and cancel require ownership. There is no administrative bypass in v1, because the gateway does not propagate roles. A non-owner receives `NOT_FOUND`, indistinguishable from a missing order.
3. **Request shape:** `UNSPECIFIED` enum values are rejected. `idempotency_key` is required (`IDEMPOTENCY_KEY_REQUIRED`). Rejecting unknown JSON fields is the gateway's job.
4. **Supported values:** `order_type` must be `LIMIT`, or `MARKET` when `ORDER_MARKET_ENABLED` is true. Otherwise `ORDER_TYPE_NOT_SUPPORTED`.
5. **Quantity:** A positive multiple of the quantity step (`QUANTITY_PRECISION_INVALID`), within the configured min and max (`QUANTITY_OUT_OF_RANGE`).
6. **Price:**
   - LIMIT: a price is required, a positive multiple of the price tick (`PRICE_PRECISION_INVALID`), within the band (`PRICE_OUT_OF_RANGE`). A missing price is `INVALID_ORDER`.
   - MARKET: the price is an optional protection price, with the same tick and band checks. If omitted, the Order Service uses the band maximum for BUY and the band minimum for SELL and sets `price_defaulted`. If `protection price required` is true, an omitted price is `INVALID_ORDER`.
7. **Delivery slot:**
   - The start is aligned to `:00` or `:30` UTC and the end is exactly 30 minutes later (`SLOT_INVALID`).
   - `now < delivery_slot_start`. This is the gate closure (`ORDER_SLOT_EXPIRED`).
   - The start is no later than `now` plus the booking horizon (`SLOT_TOO_FAR`).
8. **Idempotency lookup:** Look up `(user_id, idempotency_key)`. A match with the same fingerprint is a replay. A match with a different fingerprint is `IDEMPOTENCY_CONFLICT`. This runs before IoT calls so a replay never fails because of a later IoT outage.
9. **House and grid zone:** Resolve the user's house through the IoT service. No house returns `METER_NOT_REGISTERED`. More than one returns `HOUSE_AMBIGUOUS` (v1 supports one trading house per user). An unmapped grid returns `GRID_ZONE_UNMAPPED`.
10. **SELL eligibility:** Meter status, reading freshness, and sellable energy (next section).
11. **Concurrency-safe persistence:** The creation transaction re-checks everything that must not race: duplicate keys, energy allocation, and lifecycle state.

Validation failures return a documented error and never produce a row, an outbox record, or a Kafka message. MARKET orders and their price protection are out of scope for v1, because the proto, the engine, and the engine plan support LIMIT only.

SELL Energy Validation
----------------------

**Integration.** The Order Service uses `gridx.iot.v1.IotService` and never reads IoT Redis or TimescaleDB directly.

- IoT defines ownership as an `APPROVED`, `PRIMARY_OWNER` meter registration. A user with a pending, rejected, or expired registration sees no house.
- IoT treats an empty `owner_user_id` as "no ownership check". The Order Service therefore **always** sends a non-empty `owner_user_id` on every IoT call.
- IoT has no authentication interceptor. Only the gateway and trusted internal services may reach it, enforced at the network level.

| Step | RPC | Used for |
|---|---|---|
| 1 | `ListHouses(owner_user_id, page_size=2)` | House, `meter_id`, `grid.grid_id`, `meter_status`, `last_heartbeat_at`, `rated_solar_kw`. Empty list gives `METER_NOT_REGISTERED`. More than one gives `HOUSE_AMBIGUOUS`. |
| 2 | `GetLatestReading(house_id, owner_user_id)` | Measurement timestamp for freshness. SELL orders only. |

BUY and SELL both call step 1 to find the grid. `grid_zone_id` is resolved from `grid_id` through the interim configuration map `ORDER_GRID_ZONE_MAP`, validated at startup, because IoT `Grid` has no numeric zone ID yet. It is replaced by an IoT `grid_zone_id` field once that exists.

**Eligibility checks (SELL).**

1. `meter_status` must be online, otherwise `METER_OFFLINE`.
2. The latest reading must be no older than the max age, otherwise `READING_STALE`. A missing reading counts as stale.
3. `rated_solar_kw` must be set and positive, otherwise capacity is zero (`ENERGY_INSUFFICIENT`).
4. The quantity must fit in the remaining slot capacity, otherwise `ENERGY_INSUFFICIENT`.

Both online status and a fresh reading are required. If IoT is unavailable or times out, the order fails closed with `IOT_UNAVAILABLE` and nothing is persisted.

**Definition of sellable energy (v1).** Telemetry reports instantaneous power in kW and cannot size an order for a future slot, so v1 is capacity-based:

`slot_capacity_wh = floor(rated_solar_kw * 500)`

- The latest reading proves the meter is live and current. It does not size the order.
- Battery and V2G capacity are excluded in v1. Stored energy can be discharged only once, so counting it in every slot would oversell across slots.
- This is a physical upper bound, not a forecast. Validation does not guarantee delivery.
- The rule sits behind a `SellableEnergyPolicy` interface so a historical estimate (from `GetEnergySeries`) or the AI/ML forecast can replace it later.

**Allocation ledger (overselling protection).** An IoT reading is evidence, not a reservation. The Order Service owns the ledger:

- `energy_slot_capacity(meter_id, delivery_slot_start, allocated_wh)` with a check that `allocated_wh` stays between 0 and `capacity_wh`. The row is created on first use and the capacity computed for each request is used in the conditional update and stored on success, so a change in rated capacity takes effect on the next order.
- `energy_allocations(order_id, meter_id, delivery_slot_start, allocated_wh, released_wh, released_at)`.

Allocation is a single atomic conditional update inside the creation transaction: increase `allocated_wh` by the quantity only where `allocated_wh + quantity <= capacity_wh`. Zero rows updated means `ENERGY_INSUFFICIENT` and a rollback. A separate "check then insert" is not used. Concurrent SELL orders serialize on the capacity row. Serialization or deadlock failures are retried up to three times, then surface as `ENERGY_ALLOCATION_CONFLICT` (retryable).

| Event | Effect on the ledger |
|---|---|
| SELL order created | `allocated_wh` increases by the quantity, in the creation transaction |
| Fill | No change. Filled energy stays consumed. |
| `CANCEL_PENDING` | No change. Nothing is released on a request. |
| `CANCELLED`, `EXPIRED`, `REJECTED` | Remaining quantity is released once, in the same transaction as the status change. `released_at IS NULL` prevents a double release. |
| `FILLED` | Nothing to release |

Documented limits of v1 protection: capacity is an upper bound rather than a forecast, filled energy is not reconciled against actual metered delivery, and one house maps to one ledger key.

Idempotency
-----------

- **Field:** `CreateOrderRequest.idempotency_key`, 8 to 64 characters from `[A-Za-z0-9_-]`. A UUIDv4 is recommended. The gateway maps the client's `Idempotency-Key` header into this field. The Order Service owns the authoritative record.
- **Scope:** `(user_id, idempotency_key)`, enforced by a unique index on `orders`. The key lives on the order row, so no separate idempotency table or expiry job is needed.
- **Fingerprint:** SHA-256 of `side`, `order_type`, `requested_price`, `quantity_wh`, and `delivery_slot_start`.
- **Same key, same fingerprint:** no new order. The RPC returns `OK` with the order's current state and `replayed = true`.
- **Same key, different fingerprint:** gRPC `ABORTED` with reason `IDEMPOTENCY_CONFLICT`.
- **Concurrent requests with the same key:** the order `INSERT ... ON CONFLICT (user_id, idempotency_key) DO NOTHING` is the first statement in the transaction. The loser inserts zero rows, allocates nothing, rolls back, and replays or conflicts. A duplicate never allocates energy.
- **Rejected requests** are not stored and are validated again on retry.
- **Cancellation** is idempotent by `order_id` and needs no key.

Order States
------------

`PENDING_VALIDATION` is dropped, because validation completes before persistence and no row exists for an unvalidated order. `PENDING_PUBLICATION` becomes `PENDING`, because "published but not yet acknowledged" is not a separate client-visible state.

| Status | Proto `OrderStatus` | Meaning | Terminal |
|---|---|---|---|
| `PENDING` | none (local) | Durably recorded, not yet acknowledged by the Matching Engine | No |
| `OPEN` | `ORDER_STATUS_NEW` | Acknowledged and resting with no fills (`remaining == quantity`) | No |
| `PARTIALLY_FILLED` | `ORDER_STATUS_PARTIALLY_FILLED` | Resting with `0 < remaining < quantity` | No |
| `CANCEL_PENDING` | none (local) | Cancellation requested, outcome unknown. Fills still update quantities. | No |
| `FILLED` | `ORDER_STATUS_FILLED` | `remaining == 0` | Yes |
| `CANCELLED` | `ORDER_STATUS_CANCELLED` | Cancelled by the engine. Earlier fills are retained. | Yes |
| `EXPIRED` | `ORDER_STATUS_EXPIRED` | Slot ended unmatched. A partial fill is retained. | Yes |
| `REJECTED` | `ORDER_STATUS_REJECTED` (new) | Refused by the engine | Yes |

`OPEN` has one meaning everywhere: accepted by the Matching Engine and resting with no fills. It is the Order Service and API name for the proto value `ORDER_STATUS_NEW`. The proto has no `REJECTED` today, so one additive enum value is required.

**Transitions.** The Matching Engine owns every transition except those started by a user request or an Order Service decision.

| From | To | Trigger | Owner |
|---|---|---|---|
| (none) | `PENDING` | Creation transaction commits | Order Service |
| `PENDING` | `OPEN`, `PARTIALLY_FILLED`, `FILLED`, `REJECTED` | `OrderUpdated` with higher `order_seq` | Matching Engine |
| `OPEN`, `PARTIALLY_FILLED` | `PARTIALLY_FILLED`, `FILLED`, `EXPIRED`, `CANCELLED` | `OrderUpdated` | Matching Engine |
| `PENDING`, `OPEN`, `PARTIALLY_FILLED` | `CANCEL_PENDING` | `CancelOrder` | Order Service |
| `CANCEL_PENDING` | `CANCELLED`, `FILLED`, `EXPIRED` | Terminal `OrderUpdated` | Matching Engine |
| `CANCEL_PENDING` | stays `CANCEL_PENDING` (quantities updated) | `OrderUpdated` reporting `PARTIALLY_FILLED` | Matching Engine |
| any non-terminal | `EXPIRED` | Reconciler fallback (`terminal_source = RECONCILER`) | Order Service |

Every other transition is invalid. Terminal states are never changed by duplicate or stale events.
A MARKET order never rests, so it never reaches `OPEN` or `PARTIALLY_FILLED`. Its path is `PENDING` to `FILLED`, `CANCELLED`, `REJECTED`, or the reconciler's `EXPIRED`. `CancelOrder` is accepted only while the order is `PENDING`. Terminal `CANCELLED` for a MARKET order carries `status_reason` of `NO_LIQUIDITY` (nothing matched) or `IOC_REMAINDER` (partly matched, fills retained). SELL allocation for the cancelled remainder is released as for any terminal order.

State Management and Concurrency
--------------------------------

Durable order state lives in PostgreSQL (`order_management_data`). Two counters do different jobs: `version` is the Order Service's row version for local transitions, and `me_seq` is the last Matching Engine sequence applied.

**Matching Engine contract.**

| Topic | Producer | Consumer | Key | Payload |
|---|---|---|---|---|
| `gridx.orders.v1` | Order Service | Matching Engine | `order_id` | `OrderAccepted` (placement), `OrderCancelRequested` (cancel) |
| `gridx.orders.updates.v1` | Matching Engine | Order Service, Notification | `order_id` | `OrderUpdated` |
| `gridx.trades.v1` | Matching Engine | Settlement, Market Data, Notification | `trade_id` | `TradeExecuted` |

The Order Service does not consume `gridx.trades.v1`. `order-placements`, `completed-trades`, and the unversioned `orders` and `trades` names are retired.

- The first `OrderUpdated` for an order is the acknowledgement: `NEW` means accepted, `REJECTED` means refused, and a fill status means it matched on arrival. There is no separate acknowledgement topic.
- `remaining_quantity` is cumulative and absolute, never a delta. With a strictly increasing per-order `order_seq`, a stale event can be discarded safely because any newer event already includes the older fill.
- A missing acknowledgement is not a failure. The order stays `PENDING`, and an alert fires when its age exceeds the `PENDING` age threshold.

**Matching Engine changes required** (none exists in the engine today):

1. Publish an `OrderUpdated` for the **incoming** order. Today only resting orders are published, so an accepted order is never acknowledged.
2. Publish `REJECTED` with a reason when validation fails. Today the validation result is ignored and failed messages are skipped.
3. Add `order_seq`, a real UUID `event_id` (currently an empty string), `causation_id`, and a reject reason to `OrderUpdated`.
4. Set Kafka record keys (`order_id` for updates, `trade_id` for trades). Today records are sent unkeyed, so per-order ordering is not guaranteed.
5. Ignore a placement whose `order_id` it already holds, and a cancel whose command `event_id` it already processed.
6. Handle `OrderCancelRequested`. Reply to a cancel for an already-terminal order with an `OrderUpdated` carrying that status and a new `order_seq`.
7. Publish expiry updates (the expiry manager currently changes in-memory status without publishing).
8. Do not skip a failed message when a later offset is committed.
9. See the engine change checklist in the Matching Engine integration document.
10. Accept `ORDER_TYPE_MARKET`. Never insert a MARKET remainder into the book. Publish exactly one final `OrderUpdated` per MARKET order with `FILLED` or `CANCELLED` and a reason.
11. Reject any order arriving after `expires_at` with `REJECTED` and reason `ORDER_EXPIRED`.

**Applying an update.** For every `OrderUpdated`, in one transaction:

1. Insert `event_id` into `processed_events`. If it already exists, the event is a duplicate: commit and advance the offset.
2. Lock the order row (`SELECT ... FOR UPDATE`).
3. If `order_seq <= me_seq`, the event is stale. Do not change state, count it, and commit.
4. An echo (same status and remaining quantity as stored, with a newer `order_seq`) updates only `me_seq`, with no state change and no alert.
5. Check the transition table, that `0 <= remaining <= quantity`, and that `remaining` does not exceed the stored value. A violation sets `needs_reconciliation`, quarantines the event, and applies nothing.
6. Apply status and `remaining_quantity_wh`, set `me_seq`, increment `version`, append `order_status_history`.
7. On a terminal status, set `terminal_source = 'ME'` and release unused SELL allocation.
8. Commit, and only then commit the Kafka offset.

**Cancellation.**

- Allowed from `PENDING`, `OPEN`, `PARTIALLY_FILLED`. If already `CANCEL_PENDING`, return `OK` with the current state (idempotent). If terminal, return `ABORTED` with `ORDER_NOT_CANCELLABLE`.
- One transaction sets `CANCEL_PENDING`, writes history, and writes an `OrderCancelRequested` outbox row with a fresh `event_id`. The allocation is untouched.
- The cancel is published on `gridx.orders.v1` with the same key (`order_id`) as the placement, so the engine sees both in order. A Kafka header `x-message-type` distinguishes `order.accepted` from `order.cancel_requested`.

**Cancel versus fill.** The engine's processing order is authoritative and is expressed by `order_seq`.

| Outcome | Result |
|---|---|
| Cancel wins | `CANCELLED`. Remaining quantity is released. |
| Fill before cancel, still resting | Stays `CANCEL_PENDING`, quantities update, final outcome follows. |
| Fully filled before cancel | `FILLED`. The cancel lost the race. Nothing is released. |
| Already terminal at the engine | The engine echoes the terminal status with a new `order_seq`. `CANCEL_PENDING` resolves to it. |
| Duplicate or stale outcome | Ignored by the `order_seq` check. |
| Timeout with no outcome | Stays `CANCEL_PENDING`. A timeout is never treated as success or failure. |

**Event after a terminal state.** If `terminal_source = RECONCILER`, a higher-`order_seq` engine event supersedes it, the correction is written to history, and allocation is adjusted idempotently. If `terminal_source = ME`, the event indicates an engine inconsistency: state is unchanged, the event is quarantined, `needs_reconciliation` is set, and an alert fires.

**Expiry.**

- Each order is valid for exactly its 30-minute slot, and `expires_at = delivery_slot_end`.
- The Matching Engine is authoritative. It removes unmatched quantity at slot end and publishes `EXPIRED`.
- Fallback: for a non-terminal order where `expires_at + grace < now` and no event has arrived, a reconciler applies `EXPIRED` with `terminal_source = RECONCILER` and raises an alert. A late engine event can still supersede it.
- A partially filled order that expires keeps its fills (`EXPIRED` with `remaining_quantity_wh > 0`).
- Expiry is idempotent and releases unused SELL allocation once.

**Creation transaction.** External calls happen before the transaction. No transaction is held open across IoT, Auth, or Kafka.
**Expiry.** A MARKET order expires `MARKET TTL` after creation, not at slot end. The reconciler applies the same fallback after `expires_at` plus the grace period.

1. Ensure the user's `trader_accounts` row exists (`INSERT ... ON CONFLICT DO NOTHING`) and read `trader_id`.
2. `INSERT` into `orders ... ON CONFLICT (user_id, idempotency_key) DO NOTHING RETURNING`. Zero rows means a concurrent duplicate: roll back and replay or conflict.
3. SELL only: ensure the capacity row exists, run the conditional allocation `UPDATE`, and insert `energy_allocations`. Zero rows updated rolls back with `ENERGY_INSUFFICIENT`.
4. Insert the initial `order_status_history` row (`NULL` to `PENDING`).
5. Insert the `OrderAccepted` outbox row. Its `event_id` is generated here and reused on every republish.
6. Commit.

**Outbox publisher.**

- Reads committed, unpublished rows in `id` order and claims them with a 30-second lease (see the persistence document).
- A row is claimable only if no earlier unpublished row exists for the same `order_id`, which keeps placement ahead of cancel.
- Producer settings are `acks=all` with the idempotent producer. A row is marked published only after broker acknowledgement. Retries use bounded backoff, with alerts on backlog size and oldest-unpublished age.
- Delivery is at-least-once, so consumers must be idempotent. A Kafka outage never fails the API, because the order is already durable.
- Malformed, unsupported, or repeatedly failing messages go to a PostgreSQL `consumer_dead_letters` table (topic, partition, offset, `event_id`, error, payload), matching the IoT service's convention. An update for an unknown `order_id` is quarantined and alerted.
- `processed_events` retention must exceed topic retention (default 7 days). The permanent `me_seq` check still rejects stale events after old rows are pruned.

API Outcome Semantics
---------------------

The Order Service exposes a gRPC `OrderService` (`gridx.order.v1`, defined in the `protobuf` repository). It is called only by the API Gateway. HTTP status codes and headers belong to the gateway.

| RPC | Purpose |
|---|---|
| `CreateOrder` | Validate, persist, and queue an order |
| `GetOrder` | Retrieve one order |
| `ListOrders` | List the caller's orders (`page_size`, `page_token`) |
| `CancelOrder` | Request cancellation |

Responses distinguish the stage reached through the `status` field, not through the transport status:

| Case | gRPC status | Response |
|---|---|---|
| New order durably recorded | `OK` | `order` with `status = PENDING`, `replayed = false` |
| Idempotent replay | `OK` | `order` with its current status, `replayed = true` |
| Cancellation durably requested | `OK` | `order` with `status = CANCEL_PENDING` |
| Invalid request or `UNSPECIFIED` enum | `INVALID_ARGUMENT` | error |
| Missing or invalid identity | `UNAUTHENTICATED` | error |
| No trading permission | `PERMISSION_DENIED` | error |
| Order missing or not owned | `NOT_FOUND` | error |
| Idempotency conflict, not cancellable, allocation conflict | `ABORTED` | error |
| Business rule violation | `FAILED_PRECONDITION` | error |
| IoT, Auth, or database unavailable | `UNAVAILABLE` | error |
| Deadline exceeded | `DEADLINE_EXCEEDED` | error |
| Unexpected failure | `INTERNAL` | generic error |

A successful `CreateOrder` never implies a trade. Fills are read through `GetOrder`, `ListOrders`, or the real-time channel.

Every error carries a stable code in `google.rpc.ErrorInfo.reason`. The request ID travels in the `x-request-id` metadata key.

| Reason code | gRPC status | Retryable |
|---|---|---|
| `INVALID_ORDER` | `INVALID_ARGUMENT` | No |
| `IDEMPOTENCY_KEY_REQUIRED` | `INVALID_ARGUMENT` | No |
| `TRADING_NOT_PERMITTED` | `PERMISSION_DENIED` | No |
| `ORDER_NOT_FOUND` | `NOT_FOUND` | No |
| `IDEMPOTENCY_CONFLICT` | `ABORTED` | No |
| `ORDER_NOT_CANCELLABLE` | `ABORTED` | No |
| `ENERGY_ALLOCATION_CONFLICT` | `ABORTED` | Yes |
| `ORDER_TYPE_NOT_SUPPORTED` | `FAILED_PRECONDITION` | No |
| `QUANTITY_OUT_OF_RANGE` | `FAILED_PRECONDITION` | No |
| `QUANTITY_PRECISION_INVALID` | `FAILED_PRECONDITION` | No |
| `PRICE_OUT_OF_RANGE` | `FAILED_PRECONDITION` | No |
| `PRICE_PRECISION_INVALID` | `FAILED_PRECONDITION` | No |
| `SLOT_INVALID` | `FAILED_PRECONDITION` | No |
| `ORDER_SLOT_EXPIRED` | `FAILED_PRECONDITION` | No |
| `SLOT_TOO_FAR` | `FAILED_PRECONDITION` | No |
| `METER_NOT_REGISTERED` | `FAILED_PRECONDITION` | No |
| `HOUSE_AMBIGUOUS` | `FAILED_PRECONDITION` | No |
| `GRID_ZONE_UNMAPPED` | `FAILED_PRECONDITION` | No |
| `METER_OFFLINE` | `FAILED_PRECONDITION` | Yes, after the meter recovers |
| `READING_STALE` | `FAILED_PRECONDITION` | Yes |
| `ENERGY_INSUFFICIENT` | `FAILED_PRECONDITION` | No, unless capacity is released |
| `IOT_UNAVAILABLE` | `UNAVAILABLE` | Yes |
| `AUTH_UNAVAILABLE` | `UNAVAILABLE` | Yes |
| `INTERNAL_ERROR` | `INTERNAL` | Yes |
| `ORDER_CREATION_DISABLED` | `UNAVAILABLE` | Yes |

A Kafka or engine outage never fails creation, because the outbox absorbs it.'

### Gateway mapping

This is how the gateway translates results for REST clients, given its current implementation.

| Order Service result | Public HTTP |
|---|---|
| `CreateOrder` `OK`, `replayed = false` | `202 Accepted` |
| `CreateOrder` `OK`, `replayed = true` | `200 OK` with `Idempotency-Replayed: true` |
| `CancelOrder` `OK` | `202 Accepted` |
| `INVALID_ARGUMENT`, `FAILED_PRECONDITION` | `400` (`VALIDATION_ERROR`) |
| `UNAUTHENTICATED` | `401` |
| `PERMISSION_DENIED` | `403` |
| `NOT_FOUND` | `404` |
| `ABORTED` | `409` |
| `UNAVAILABLE` | `503` |
| `DEADLINE_EXCEEDED` | `504` |
| `INTERNAL` | `500` |

Today the gateway keeps only the message text for 4xx errors and drops `ErrorInfo.reason`. It must forward the reason as the public error code so clients can tell `ENERGY_INSUFFICIENT` from `READING_STALE`. The gateway has no orders feature or Order Service client yet, and its default gRPC deadline is 5 s, which fits the Order Service's 2 s IoT budget.

Decisions and Dependencies
--------------------------

### Resolved decisions

| ID | Open item | Decision |
|---|---|---|
| D-01 | Supported order types and MARKET protection | LIMIT and MARKET. MARKET is IOC with a protection price, behind `ORDER_MARKET_ENABLED`." Extend O-3 with: "`ORDER_TYPE_MARKET`, `incomingOutcome`, `OrderUpdateReason`, and rejecting expired orders." Add O-9: "Should a MARKET protection price be required instead of defaulting to the band bound? Owner: product.|
| D-02 | Fields, units, precision, constraints | Wh, micro-AED per kWh with a 10,000 tick, UTC timestamps, `uint64` order IDs. See Order Model. |
| D-03 | Delivery-slot and expiry rules | 30-minute slots, gate closure at slot start, 24 h horizon, `expires_at = slot end`, engine authoritative with a reconciler fallback. |
| D-04 | IoT availability semantics and overselling | `IotService` for house and freshness, capacity-based sellable energy, allocation ledger with an atomic conditional update. |
| D-05 | Idempotency scope and conflict behaviour | `idempotency_key` unique per `(user_id, key)` on the order row. Replay returns `OK` with `replayed = true`. A different payload returns `ABORTED`. |
| D-06 | Canonical state enum and transitions | Eight statuses and the transition table. `OPEN` maps to `ORDER_STATUS_NEW`. |
| D-07 | Engine acknowledgement and status semantics | First `OrderUpdated` is the acknowledgement. Cumulative quantities guarded by `order_seq`. |
| D-08 | Cancel versus fill reconciliation | Cancel command on the same topic and key as placement. Races resolved by `order_seq`. |
| D-09 | Outbox and duplicate-event handling | Per-order-ordered outbox, at-least-once delivery, dedupe in the same transaction as the state change. |
| D-10 | API response codes and retry semantics | gRPC `OrderService`, `OK` plus a `status` field for stage, gRPC statuses with `ErrorInfo.reason` for errors, gateway mapping above. |
| D-11 | User identity in events | Auth user IDs are UUIDs, but the order and trade protos use `uint64 user_id`. The Order Service issues a numeric `trader_id` per user (`trader_accounts`, created on first order) and sends it as `user_id`. An additive `string user_uuid` is added to `OrderAccepted` and to `TradeExecuted` so Settlement can credit wallets without a lookup. |
| D-12 | Implementation language | Go, like `iot-ingestion-dispatch` and `billing-wallet-service`. |

### Dependencies on other documents

- `api-contracts.md` must change: create and cancel return `202` with `PENDING` and `CANCEL_PENDING`, add `Idempotency-Key`, use `quantityWh`, string order IDs, micro-AED prices, and the gateway error envelope.
- The Matching Engine crash-recovery document and `api-contracts.md` §5.4 describe a direct gRPC recovery request. This conflicts with the Kafka-only rule and is settled in the recovery protocol document.
- The recovery active set must also include `PENDING` and `CANCEL_PENDING` orders whose slot has not ended.
- BUY order readiness and credit reservation are tracked in the cancellation and expiry plan. Billing has no reservation contract yet.
- Settlement rounding and the platform fee commission belong to Billing and Settlement.

Record these decisions in the shared contracts and in the PostgreSQL persistence document so the Order Service, API Gateway, and Matching Engine use consistent rules.
