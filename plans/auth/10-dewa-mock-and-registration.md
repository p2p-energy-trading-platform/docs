# DEWA Mock and Registration Flow

## Purpose

The DEWA application is a small external mock used to demonstrate the
smart-meter registration journey.

It is **outside the platform system boundary**.

The mock only needs to demonstrate an external authority approving a smart-meter
association request.

## Recommended DEWA Mock Stack

  Concern         Technology
  --------------- ------------------------------------------------------
  Techstack       Tanstack start + nitro
  State           In-memory initially
  Communication   HTTP/JSON

## Mock UI

The UI can contain a single page with list of requests:

``` text
DEWA Mock Customer Portal

Smart Meter Connection Requests

----------------------------------------
Meter: METER-001
Requested by: User 123

Status: PENDING

[ Approve ] [ Reject ]
----------------------------------------
```

The purpose is to make the external approval step visible during a
project demonstration.

## Mock API

Suggested endpoints:

``` text
POST /api/link-requests
GET  /api/link-requests/:requestId
POST /api/link-requests/:requestId/approve
POST /api/link-requests/:requestId/reject
```

| Method | Endpoint | Description | Request / Response Payload Example |
| :--- | :--- | :--- | :--- |
| **POST** | `/api/link-requests` | Called by your platform when a user initiates a meter claim. | **Req:** `{"registrationId": "REG-123", "meterId": "METER-001", "userReference": "USER-123"}`<br>**Res:** `{"requestId": "REQ-123", "status": "PENDING", "message": "Link request created"}` |
| **GET** | `/api/link-requests` | Called by the DEWA Mock Customer Portal UI to list all requests. | **Res:** `[{"registrationId": "REG-123", "meterId": "METER-001", "status": "PENDING", ...}]` |
| **GET** | `/api/link-requests/:requestId` | Called by your platform to poll or check the approval status. | **Res:** `{"registrationId": "REG-123", "meterId": "METER-001", "status": "APPROVED"}` |
| **POST** | `/api/link-requests/:requestId/approve` | Triggered when the customer clicks `[ Approve ]` in the DEWA portal. | **Res:** `{"success": true, "status": "APPROVED"}` |
| **POST** | `/api/link-requests/:requestId/reject` | Triggered when the customer clicks `[ Reject ]` in the DEWA portal. | **Res:** `{"success": true, "status": "REJECTED"}` |

The platform communicates with these endpoints over HTTP.

## In-Memory State

The DEWA mock can maintain:

``` text
pendingRequests[]
```

in RAM (memory).

This is acceptable (for now) because the DEWA application is a demonstration-only
external simulation.

**NOTE**: A restart can clear pending requests for now (acceptable for now)

## Registration Flow

### 1. Account Registration

``` text
User
  |
  v
Web/Mobile App
  |
  v
API Gateway
  |
  v
Auth Service
```

The user creates an account through the normal authentication flow.

### 2. Meter Claim

After authentication:

``` text
User
  |
  | meter ID
  v
Web/Mobile App
  |
  v
API Gateway
  |
  v
Iot Ingestion & Dispatch Service
```

The platform creates a `registrationId`.

### 3. DEWA Link Request

The platform calls:

``` text
POST /api/link-requests
```

on the DEWA Mock.

Example logical request:

``` json
{
  "registrationId": "REG-123",
  "meterId": "METER-001",
  "userReference": "USER-123"
}
```

The DEWA Mock stores the request as `PENDING`.

### 4. User Approves in DEWA Mock

The frontend opens the DEWA Mock portal.

The user sees the pending request and clicks:

``` text
Approve
```

The request becomes:

``` text
APPROVED
```

### 5. Platform Checks Approval

The platform retrieves the request status from the DEWA Mock.

If approved, the registration workflow can associate:

``` text
userId
meterId
registrationId
```

within the platform.

### 6. Completion

The platform records the smart meter as registered to the account.

**NOTE**: registration event can later be notified through other means (that part is still not decided - notification service)

## IoT Simulator Relationship

The existing IoT Simulator generates:

- Fixed grids.
- Houses at startup.
- Simulated meters.
- Telemetry in memory.

A meter ID can correspond to one of the meters generated by the
simulator.

## Boundary Rule

The external mock should interact through its public API.

Similarly, the platform should not directly access internal state inside
the simulator.

## Recommended Registration State

Use a registration state machine in the platform:

``` text
PENDING
   |
   v
DEWA_APPROVAL_PENDING
   |
   +----> REJECTED
   |
   v
APPROVED
   |
   v
REGISTERED
```

A separate `registrationId` should identify each registration attempt.

## Detailed request flow

1. Client Initiation: The user submits a meter claim from the frontend web/mobile application to the API Gateway.
1. Gateway Verification & Routing: The API Gateway authenticates the request through the Auth Service and routes it internally to the backend registration/IoT service.
1. Internal State & Outbound Call: The backend service generates a unique registrationId, persists the initial state as `DEWA_APPROVAL_PENDING`, and dispatches an HTTP `POST /api/link-requests` payload (containing `registrationId`, `meterId`, and `userReference`) to the external DEWA Mock application.
1. External Approval: The user approves the request inside the DEWA Mock Customer Portal UI, updating its internal status to `APPROVED`.
1. Status Verification & Finalization: The platform checks the request status via `GET /api/link-requests/:requestId`. Once confirmed, the platform transitions the registration state machine to APPROVED and then REGISTERED, locking in the `PRIMARY_OWNER` association within the platform database.

## Future Cryptographic Registration

**Deferred implementation note:**

Cryptographic device registration should be implemented later as a
separate enhancement.

The intended future model is:

``` text
IoT Simulator
    |
    | generates key pair
    |
    +--> private key remains with simulator
    |
    +--> public key is registered with the platform
```

The simulator can then sign telemetry using its private key:

``` text
Telemetry + Signature
        |
        v
MQTT
        |
        v
Kafka
        |
        v
IoT Ingestion
        |
        v
Verify using registered public key
```

The DEWA Mock should not generate or possess the IoT meter's private
key.

When cryptographic registration is implemented, the exact enrollment
mechanism (one-time enrollment credential, registration token, device
bootstrap flow, and public-key submission API) should be designed
separately in the future implementation.
